# fbfast 0.2.1 — Security boundaries and bounded materialization

This maintenance release bounds materialized results by default, updates the
native dependency chain, and makes the library's read-only security boundary
explicit.

## Added

- A 512 MiB default `max_result_bytes` budget for each result materialized as
  rows, dictionaries, Pydantic models, JSON, Arrow, or Polars. It can be changed per
  connection or disabled explicitly with `None`; streams retain batch-based
  limits.
- A documented security model and disposable-fixture tests showing why
  read-only transactions and SQL filtering do not make privileged routines a
  sandbox.
- A single `./scripts/release.py` command that validates the release, creates
  and pushes its commit, waits for CI, tags the verified commit, waits for PyPI,
  and creates the GitHub Release. Interrupted runs can resume safely.

## Security and maintenance

- Updated PyO3, its async runtime, and `time` to releases without the RustSec
  advisories found during the review; CI blocks releases when `cargo audit`
  reports an advisory.
- Password storage is shared through a zeroizing core buffer, and the temporary
  native attach buffer is overwritten after use. Python strings and copies made
  by the operating system or Firebird client remain outside that guarantee.
- Materialized-result limits use checked accounting and return
  `ResultLimitError` without a partial result. Cursor and transaction cleanup
  leave the pool reusable.
- Published wheels retain the pinned Firebird 5.0.3 client. The matrix tests
  servers 5.0.3 and 5.0.4; a client-only move to 5.0.4 was rejected after local
  tests exposed named-time-zone incompatibility with a 5.0.3 server.

## Compatibility

The public query APIs remain source compatible. `max_result_bytes` is again an
accepted `FirebirdConfig` option and `FB_MAX_RESULT_BYTES` environment variable.
Applications that intentionally materialize more than 512 MiB in one result
must choose a larger value or `None`.

Firebird 5.0.3 servers remain supported. Upgrading a server is recommended when
the deployment permits it because the client bundled in a wheel cannot patch a
remote server.

## Validation status

Local macOS arm64 / CPython 3.14 validation passed 264 Python integration tests,
31 live Rust/C++ tests, 26 packaging tests, and 25 model tests with 2 SDK-only
skips. The built 0.2.1 wheel passed installed-consumer smokes against disposable
Firebird 5.0.3 and 5.0.4 servers. Rustfmt, Clippy, Ruff, Mypy, module boundaries,
actionlint, fuzz-target compilation, vendor verification, and a 123-dependency
RustSec audit also passed. The source distribution built successfully and passed
`twine check`.

The tag workflow still must pass the complete 20-wheel matrix, Linux
ASan/UBSan and fuzz execution, sdist checks, artifact verification, and RustSec
audit before PyPI publication. No operational database has been homologated for
this release.
